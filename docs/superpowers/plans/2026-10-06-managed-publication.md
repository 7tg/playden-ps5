# Managed publication continuation

**Goal:** Complete the publication and retry requirements in Tasks 4–6 of the
[approved integration plan](2026-10-05-prospero-win-integration.md), for both first
installation and settings changes on an already registered title.

**Architecture:** One stable lock inode coordinates the publisher and Wine title.
A durable pending/committed receipt protects the complete settings operation,
including mutable registry and game-root DXVK effects. Each file is published
durably; this protocol does not claim an atomic cross-directory rename.

## Evidence and decisions

The current `FilesystemPackageInstaller` creates publication directories before
calling `publish_owned`. Retry then rejects existing `input/` without final
metadata as a collision. Initial ownership must be recorded before those effects.
The current wrapper treats an absent descriptor as generic mode, and reads the
profile without checking publication state. A scanner-visible per-game title
must refuse missing descriptor/publication, rather than run generic behavior.

`ApplySettingsFiles` can change `user.reg` and game-root `dxvk.conf` before profile
publication. Its immediate rollback is not a process-death transaction. A
profile-only guard would therefore leave mixed settings possible.

On PS5 FW13.60, `SYS_flock` (131) through the checked libkernel gateway passed
nonblocking shared/exclusive contention and close-release across independent open
descriptions in a fresh owned fixture. See
[native evidence](../../../results/20261006-managed-filesystem/launch-lock-native.log).
Cross-process wrapper/publisher acceptance remains required. Do not assume the
SDK's named `flock` import works solely because its stub exists.

Use these canonical paths under each owned `/data/playden/games/<install>`:

- `.playden-control/publication.lock`: owned `0600` regular file, stable inode;
  never rename, truncate or delete it during publication or game execution.
- `.playden-control/publication-state.v1`: durable bounded pending/committed
  receipt, separate from final `.playden-publication` metadata.
- `.playden-control/publication-operation.v1`: frozen operation journal and
  recovery snapshot references. Backups remain private and ownership-bound.

The control directory is owned `0700`. Initial setup requires positively stopped
native activity, owned title/bottle markers, destination absence and existing
install reservation. It cannot retroactively adopt foreign profile/input files.

Receipt schema 1 is strict JSON, bounded at 8192 bytes, with these fields:
`schema_version`, `phase` (`pending` or `committed`), `transaction_id` (canonical
UUID), `install_id`, `title_id`, `kit_id`, `runtime_bundle_id`, `recipe_id`,
`recipe_version`, `previous_revision`, `settings_revision` (exact uint64),
`plan_sha256`, and `publication_sha256`. The last digest is empty while pending;
when committed it binds the exact schema-2 completion metadata. Reject unknown
fields, duplicate fields, unsupported versions, malformed digests and identity
drift. `previous_revision` must not exceed `settings_revision`;
initial `previous_revision` is zero; a pending receipt preserves the
previous committed revision and never implies it is safe to launch.

Completion metadata schema 2 retains the strict flat LF marker format and the
existing bounded identity/revision/profile/descriptor/input fields, replacing
`input.N.name` with hex-encoded `input.N.name_hex`. Input names are unique under
case-insensitive comparison, single safe filenames ending in `.input`. It adds
`catalog_sha256`, `dxvk.path_hex`, `dxvk.present` (exactly `0` or `1`),
`dxvk.sha256` (empty when absent), and `registry_count`. The canonical DXVK path
is required even when absent, so the absence expectation has an explicit target. Every registry entry
requires `registry.N.key_hex`, `.name_hex`, `.kind` (`absent`, `string`, `dword`),
`.string_hex`, and `.dword` (eight lowercase hex digits for a DWORD). Fields that
do not apply must be empty. Reject unknown/duplicate fields, missing indices,
surplus entries and schema 1 in guarded variants.

Hex-encode semantic strings, paths, keys and value names to avoid divergent C/C++
handling of Wine backslashes, quotes and marker delimiters. Bound total metadata
at 32768 bytes, inputs at 64, decoded input names at 64 bytes, registry entries at
2, keys at 1024 bytes, names/strings at 64 bytes, and paths at 512 bytes. Raise the
installer's existing 4096-byte metadata read limit consistently. Both native and
OWNER use one portable parser; validate generated bytes before publishing them.

The catalog must contain exactly the expected profile filename plus newline.
Derive the permitted DXVK path from the verified profile's working directory;
metadata cannot authorize another path. Verify an owned regular file's digest
when present, and actual absence when absent. Derive `user.reg` from the verified
bottle and compare the intended values semantically. Reject duplicate target
sections/assignments using case-insensitive identity matching. Only the current
owned keys are supported: executable-specific `Version` and
`Control Panel\Desktop\LogPixels`. Unrelated legitimate Wine rewrites are
accepted; do not hash the whole live registry. Recovery snapshots and operation
digests bind intended edits and owned DXVK bytes.

## Task C: Journaled OWNER publication and recoverable first retry

**Files:** new `src/runtime/settings_publication.cpp` and
`tests/runtime_settings_publication_test.cpp`; extend

**Interfaces:** `PublishSettingsOperation(const SettingsPublicationOperation&,
const PublicationPaths&, PublicationDependencies&)` returns
`PackageActionResult`. Dependencies provide durable operation storage, the shared
lock/receipt adapter, positively stopped native activity, actual hash operations
and existing OWNER parsers. Freeze the supplied plan and record; a changed recipe
or revision requires a new operation, never changes a recovering transaction.
The operation contains the install record, complete settings launch plan,
profile/input/descriptor publication bytes, transaction ID and previous revision.
Durable recovery loading distinguishes absent, valid, corrupt and unavailable;
do not conflate these states through an optional snapshot. Large registry backups
use private transaction-specific files bound by digest.

The first independently testable increment is the immutable operation codec and
private backup store, before live publisher effects. Use explicit recovery states
(`absent`, `valid`, `corrupt`, `unavailable`) and an exclusive operation file.
Store shared profile/input bytes only once in the complete launch plan; rebuild
`ProfilePublication` from the frozen identities and those validated bytes. Never
serialize and later trust `profile_references_validated`. Preserve composed
profile arguments separately from the install/adoption record's launch arguments;
they legitimately differ and are both frozen.

Bound the canonical length-prefixed operation at 2 MiB, with lengths/counts
checked before allocation and exact EOF. A 1 MiB limit is insufficient for
64 input files plus both prior/desired DXVK contents and metadata/receipts.
Keep registry backups outside the operation, at most 32 MiB, in exact-owned-0600
transaction-named files beneath the existing control directory; bind their size,
original mode, filename and digest in the frozen operation. Avoid an unjournaled
backup child-directory lifecycle. Write/sync the exclusive backup before the
exclusive operation journal, then the pending receipt, then live effects. A
pre-journal orphan grants no ownership or readiness.

Cross-validate the frozen record/plan, pinned profile/input/descriptor parsers,
shared schema-2 metadata and both receipt phases on creation and recovery. A
canonical freeze digest can cover intended bytes and before-state/backup bindings,
excluding the two receipts and digest field to avoid circular hashing. Receipts
bind that digest and the committed receipt also binds exact metadata bytes. A
missing or altered referenced backup prevents valid recovery. Exact 0600 policy
must be established independently of Storage's legacy 0644 allowance.

Acquire publisher ownership, persist the operation journal, then sync pending
receipt before creating profile/input directories or invoking `ApplySettingsFiles`.
Retain typed snapshots and backups needed to verify/reconcile registry/DXVK
changes. Publish profile/catalog/input/descriptor/metadata with individual file
and parent barriers; verify the complete resulting set. Persist/sync committed
receipt last, then reconcile the OWNER record. Any failure keeps readiness
blocked and preserves recovery evidence; a failed rollback does not clear pending.
Initial retry accepts only its matching receipt/operation snapshot or verified
committed metadata. Unknown files or changed identities remain collisions.

Read-only preparation audit confirmed these changes are necessary: the installer
currently writes/checks schema 1 and a profile-only success shortcut, creates
publication directories before the callback, and uses final metadata as initial
retry ownership proof. Replace that shortcut with complete committed receipt and
semantic settings verification. Generate schema 2 through the shared serializer,
including catalog/input/DXVK/registry expectations and its 32768-byte bound.
Validate exact `0600` control files separately from durable Storage's legacy
`0644` read allowance. The existing settings helper's immediate rollback and
fixed backup name do not supply durable transaction recovery.

Keep the publisher lease through committed receipt verification. Initial install
still needs native registration before Ready; registered-title settings updates
verify that registration without restaging the bottle/title. A failed Ready write
reconciles the committed operation without reallocation, repeated registration or
settings application. Positive stopped-activity checking remains a caller duty,
separate from file locking.
